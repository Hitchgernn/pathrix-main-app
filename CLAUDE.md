## What this project is

PATHRIX — a WebGIS AI agent for multimodal mobility navigation in Yogyakarta (TransJogja bus, KRL rail, YIA airport rail, plus andong/becak first/last-mile), built for the MAPID WebGIS Competition 2026. Full detail lives in `docs/ARCHITECTURE.md`; `docs/PLAN.md` has the build plan and schedule. **When the docs and the eventual code disagree, the code is right and the docs are stale — update the relevant doc in the same change that invalidates it** (`docs/ARCHITECTURE.md` §16).

## Architectural principles (the load-bearing decisions)

These five, from `docs/ARCHITECTURE.md` §2, are re-architectures if changed, not refactors:

1. **The LLM orchestrates; it never computes.** Every number the user sees (distance, duration, fare, CO₂) comes from a deterministic tool call and is interpolated into the response — never generated by the model. This must be structural (responses assembled from typed tool returns), not a system-prompt request for honesty.
2. **Prose and map commands travel on separate channels.** The agent emits two independent streams over one WebSocket: streamed text for chat, and structured `UICommand` objects for the map. The client never parses instructions out of prose.
3. **Time-independent routing.** No GTFS feed exists for TransJogja, so service is modeled by headway (not timetable) — meaning edge cost is time-independent and plain Dijkstra is correct. No timetable simulation, no time-expanded graph.
4. **Mirror external data; do not proxy it.** MAPID mission data is ETL'd into PostGIS on a schedule; viewport queries hit the local mirror, never the live MAPID API.
5. **Degrade, don't fail.** Every external dependency (LLM, routing graph, MAPID mission API, basemap, Nominatim, Redis, PostGIS) has a defined degraded behavior — see the failure-mode table in `docs/ARCHITECTURE.md` §13. Only PostGIS being down is unsurvivable.

## Planned module layout and dependency rule

```
backend/app/
  api/       HTTP + WebSocket surface, auth, rate limiting, payload validation — no business logic
  agent/     LangGraph graph, tool bindings, prompts, LLM adapter — never computes numbers, never touches DB directly
  routing/   graph construction, Dijkstra variants, isochrones, TSP — no HTTP, no LLM, no MAPID knowledge; must be importable/testable with no network
  data/      PostGIS repositories, MAPID adapter, geocode resolver, ETL — no routing algorithms
  models/    Pydantic schemas — the shared API contract; must not import from any other layer
frontend/src/
  components/  map, agent bottom sheet, layer panel, itinerary
  lib/         websocket client, map<->agent state bridge (`lib/bridge.ts`)
  styles/      Tailwind theme (tokens copied from the sibling landing-page repo, not cross-imported)
data/
  digitization/  TransJogja/KRL route digitization notebooks
  survey/        MAPID Apps field survey exports + QC scripts
  fixtures/       sample payloads for offline dev/tests
```

**Dependency rule:** `api → agent → {routing, data} → models`. Nothing depends upward.

Stack (see `docs/PLAN.md` §3 for full rationale): FastAPI + Uvicorn, LangGraph (not the classic LangChain `AgentExecutor`), PostgreSQL 16 + PostGIS 3.4, GeoPandas/Shapely/OSMnx/NetworkX for spatial/graph work, Redis 7 for caching, Vite + React 18 + TypeScript + Zustand + Tailwind 4 on the frontend, MapLibre GL JS with MAPID MAPS as the basemap (plain style-spec v8 URL, no SDK).

## The five agent tools (fixed surface — do not add a sixth casually)

Exactly the five named in the competition PRD; the API contract with judges depends on this surface staying five tools (`docs/ARCHITECTURE.md` §8.3):

```python
def toggle_layer(layer_id: str, on: bool) -> LayerResult
def get_data_in_viewport(bbox: BBox, data_type: str, limit: int = 50) -> FeatureList
def calculate_route(start: str | Coord, end: str | Coord, modes: list[str], optimize: Literal["termudah","tercepat","termurah"]) -> Route
def plan_multistop(stops: list[str | Coord], optimize: str) -> Itinerary
def calculate_carbon_savings(route: Route) -> CarbonResult
```

Place-name resolution (Nominatim, via `nominatim.mapid.io`) is an internal helper called inside `calculate_route`/`plan_multistop`, not a sixth tool — see `docs/ARCHITECTURE.md` §6.5.

## MAPID integration specifics worth knowing before writing the adapter

- Two separate API keys with different exposure profiles — never conflate them: `MAPID_BASEMAP_KEY` (public, reaches the browser via the style URL) and `MAPID_MISSION_API_KEY` (server-only, must never appear in a bundle, proxied response, or log line).
- Mission endpoint is spelled **`struckgo`**, not `strukgo`.
- Two distinct response shapes across the four mission datasets (`menugo`/`propertigo`/`struckgo` vs `activities`) — do not write one parser for both; normalize via the `MissionPage` type in the adapter (`docs/ARCHITECTURE.md` §6.4).
- Only missions with status `"Diterima"` are ever returned by MAPID — this is hardcoded server-side, not a filter you control.

## Testing strategy (once code exists)

Per `docs/ARCHITECTURE.md` §14 / `CONTRIBUTION.md`: `routing/` gets pure unit tests on synthetic graphs (no network, no LLM, no DB). `data/` tests against a `FakeMapidClient` fixture, not the live API, unless specifically verifying the real contract. `agent/` changes touching a tool or prompt must be run against the ≥30-prompt Indonesian intent-precision fixture set before merging — it's the actual ≥80% scored metric, not a proxy for it.
